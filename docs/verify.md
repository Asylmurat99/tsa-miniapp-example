# Проверка конверта

HMAC-SHA256 на вашем секрете, результат - шестнадцатеричная строка нижним регистром, 64 символа. Одним и тем же способом проверяются [контекст запуска](/launch-context) и конверт [`getPhone`](/bridge/get-phone): отличается только имя поля с подписью.

1. Взять все поля, кроме поля с подписью, в декодированном виде.
2. Отсортировать ключи по алфавиту.
3. Собрать строку из пар `ключ=значение`, пары разделить переводом строки `\n`.
4. Взять HMAC-SHA256 от строки в UTF-8 и сравнить с подписью - сравнением, устойчивым по времени.

Поле с подписью: `hash` в контексте запуска, `sign` в конверте `getPhone`.

## Порядок проверок

Подпись идёт первой: пока она не сошлась, ни одно поле ничего не значит.

1. Подпись. Не сошлась - отказать.
2. `auth_date` в окне 300 секунд **в обе стороны** от вашего текущего времени.
3. `nonce`, если вы ведёте реестр предъявленных значений.
4. `app_id` равен вашему.
5. Ветвление по `auth` - только после того, как всё выше прошло.

## Тестовый вектор

Секрет `my_secret_key`. На этих трёх случаях можно прогнать свою реализацию, не имея настоящего секрета.

| Случай | Ожидаемая подпись |
|---|---|
| Запуск абонентом | `72408ed73eebbc71d35b750b683eabdd8825916925350e7eb5ffb67e3ca74f12` |
| Запуск гостем (тот же набор без `user`, `auth=guest`) | `f5dd78e4c8d5bd585ced48e3b21b552c9d3e5448646d1d0469cc2ec288cf5bb6` |
| Конверт `getPhone` | `2faf04cc47bef45ce6607a20d3703b101730b6ceb602295e3b8c818e2bc4bd83` |

Каноническая строка первого случая - то, от чего берётся HMAC:

```
app_id=34d5810c-7c36-11eb-82e7-f2189812cd57
auth=customer
auth_date=1755388800
nonce=7c9e6679-7425-40de-944b-e07fc1f90ae7
platform=ios
start_param=channels
user={"id":"3f1a9c40-77ad-4e0f-9c3d-11c2a0f5e881"}
```

Завершающего перевода строки нет. Поле `hash` в строку не входит.

Все три случая целиком, вместе с исходными строками запроса и JSON конверта, лежат в `verify/vector.json` репозитория.

## Строка, а не объект

`/api/session` в примере принимает контекст строкой, а не объектом. Так и надо делать у себя: если разобрать контекст на клиенте и отправить бэкенду JSON, теряются порядок и кодирование полей - а подпись посчитана ровно по исходным байтам, и после пересборки она не сходится. Тот же приём в `/api/phone`: конверт уходит бэкенду целиком, таким, каким его выдало приложение. Оба обработчика - в `server/handlers.go`.
