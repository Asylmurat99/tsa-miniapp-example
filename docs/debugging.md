# Отладка

## Локальная подпись контекста

Пока мини-апку некому запускать, контекст можно подписать самому - тем секретом, что лежит в вашем `.env`:

```bash
# контекст абонента: <uuid> станет полем user.id
go run ./server -sign -sign-user <uuid>

# гостевой контекст: без user и scope
go run ./server -sign

# контекст абонента с правом phone:read
go run ./server -sign -sign-user <uuid> -sign-scope phone:read
```

```bash
go run ./server -sign -sign-user <uuid> \
  | python3 -c 'import sys, urllib.parse
print("http://localhost:8080/app/#tsaWebAppData="
  + urllib.parse.quote(sys.stdin.read().strip(), safe=""))'
```

Каждая из этих команд печатает готовую строку контекста и завершается. Конвейер ниже сразу печатает адрес, который можно открыть в браузере. Мини-апка отправит контекст своему бэкенду, тот проверит подпись, поднимет сессию по `user.id` и покажет, кто пришёл.

Так проверяется весь путь от чтения фрагмента до сессии, без приложения и без туннеля. Начинайте с контекста абонента без прав: это то, что получит большинство мини-апок. Вариант с `-sign-scope` полезен, чтобы увидеть, как экран показывает и прячет кнопку номера по полю `scope`; сам вызов `getPhone` в браузере не сработает, мост есть только внутри приложения.

## Постоянный адрес для разработки

Приложение открывает только `https` и только тот адрес, который зарегистрирован за вашей мини-апкой. Регистрируется он один раз, а меняется только через менеджера, поэтому адрес для разработки должен быть постоянным. Быстрый туннель вроде `cloudflared tunnel --url`, который получает случайное имя при каждом запуске, для этого не годится.

Два способа получить постоянный адрес:

| Способ | Когда подходит |
|---|---|
| Свой тестовый домен, например `https://miniapp-dev.example.kz/app/` | Есть стенд, куда можно выкладывать сборку. Самый простой вариант, если стенд уже есть |
| Туннель с фиксированным именем до локальной машины | Хочется отлаживать локальный сервер прямо из приложения |

Туннель с фиксированным именем есть у cloudflared, если ваш домен обслуживается в Cloudflare:

```bash
cloudflared tunnel login
cloudflared tunnel create miniapp
cloudflared tunnel route dns miniapp miniapp-dev.example.kz
cloudflared tunnel --url http://localhost:8080 run miniapp
```

и у ngrok со статическим доменом из личного кабинета:

```bash
ngrok http --url=<name>.ngrok-free.app 8080
```

В ngrok старше 3.10 тот же флаг называется `--domain`.

Регистрируйте адрес вместе с путём, по которому отдаётся мини-апка: `https://miniapp-dev.example.kz/app/`. Без `/app/` приложение откроет сайт документации.

## Сборка приложения с dev-окружением

Для отладки менеджер выдаёт сборку приложения, в которой можно переключить окружение, и учётную запись тестового абонента.

Дебаг-меню спрятано: вкладка **Messages** в нижней навигации, затем кнопка с жуком внизу справа. В нём - переключатель окружения и **View logs**.

**View logs** - внутренний лог приложения. Строки с префиксом `MINIAPP:` показывают, что произошло при запуске мини-апки: какой адрес открыт, что ответил шлюз, почему контейнер закрылся. Это первое место, куда стоит смотреть, когда мини-апка не открывается.

## Инспектор WebView

Мини-апка - обычная страница, к ней подключается штатный инспектор:

| Платформа | Как подключиться |
|---|---|
| Android | `chrome://inspect#devices` в Chrome на машине разработчика, устройство подключено кабелем с включённой отладкой по USB |
| iOS | Safari, меню **Develop**, затем устройство и нужный WebView |

Дальше доступны консоль, сеть и DOM, как в браузере.

## Что означают отказы

Коды из строк `MINIAPP:` в **View logs**, когда контейнер закрылся, не открыв страницу, или `getPhone` не отдал номер.

| Отказ | Причина |
|---|---|
| `403 app_not_launchable` | Мини-апка не опубликована, отключена или у неё не заведён секрет. Лечится на нашей стороне - напишите менеджеру |
| `404 phone_unavailable` | У тестового абонента нет подтверждённого номера. Мини-апка при этом работает, `getPhone` отвечает `PHONE_UNAVAILABLE` |

Отказы вашего собственного бэкенда - в [частых ошибках](/troubleshooting).
